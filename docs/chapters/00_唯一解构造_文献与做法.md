# 唯一解构造 —— 文献依据与业界做法

> **2026-11-05 查到并落盘。出发点是出题器 20 次只成 1 次，怀疑「唯一解」的做法本身有问题。**
>
> **结论：做法没问题，是我们的实现错了。而且要改的不止一处。**

---

## 一、ReverseMath：正是我们该参照的那篇

**Zhao, Liu, Du, Schütze, Hedderich (2026)**
*ReverseMath: Answer Inversion for Scalable and Verifiable Mathematical Problem Generation*
[arXiv:2605.27709](https://arxiv.org/abs/2605.27709)（LMU Munich / Saarland）

### 1.1 它的核心思想

> 给定一道题 x 和答案 y：**把题里某个数值 v 遮住，把原答案 y 当已知条件，重写题目，使 v 成为新答案。**

**这就是我们的「预指派」** —— 答案先知道，题目倒着造出来。

### 1.2 ⭐ 它最关键的一句话

> **"Because v is known, the answer to x′ is deterministic by construction."**
>
> **"The main challenge is therefore to generate a natural, solvable, and non-leaking problem with v as its unique answer."**

**翻译过来：答案确定性是构造保证的；唯一性要额外验证。**

### 1.3 它的验收标准（三条，原文）

```python
verifier checks whether the problem is
  ① uniquely solvable        ← 唯一可解
  ② free of answer leakage   ← 不泄题
  ③ answer matches masked value  ← 答案等于被遮住的值
```

**⭐ 关键：这三条是「事后验证」，不是「事前约束」。**

**它没有去约束函数集「不许等价合成」——它做的是造出来之后验一遍。**

### 1.4 它的失败处理

> "rejection sampling over candidates"
> "iterative generation"

**造出来不合格就扔掉重造，不管尝试几次。**

## 二、⭐ 这直接推翻了我们的做法

| | 我们现在的做法 | ReverseMath 的做法 |
|---|---|---|
| **唯一性** | **生成时硬性排除**（`has_equivalent_composition` 一命中就 reject 整条链） | **生成后验证**，不过就换个种子重来 |
| **代价** | 30% 的链被无条件毙掉 | 只毙掉真不合格的 |
| **对函数集的要求** | 要求函数集本身「无等价合成」 | **完全不要求** |

### 2.1 我们的做法为什么错

**`has_equivalent_composition` 问的是：「函数集里有没有 f∘g = h」。**

**但题目唯一性真正需要的是：「从起点 x₀ 出发，有没有第二条不同的运算序列能到达终点 y」。**

**这是两个完全不同的问题：**

```
前者：性质属于【函数集】
后者：性质属于【这一条具体的路径 + 这个起点终点对】
```

**函数集里有 f∘g = h，不代表模型就能用 f→g 代替 h 走通这条路径** —— 因为 f→g 必须作用在**正确的起点**上，而且中间值不能撞上别的节点。

**实测证据：**

```
全空间 210 个运算里随机抽 10 个
无等价合成的比例 = 57%
但整条链能同时满足「中间值互异 + 终点在范围」的 = 几乎 0

→ 真正的瓶颈是终点爆炸（133/200），不是等价合成（59/200）
→ 就算把等价合成全放开，合格率也只能到 67%
```

**⚠️ 所以：等价合成这条约束既错（问题问错了），又没用（不是瓶颈）。**

## 三、另一条线：CapBencher（原 PhishBencher）

**Ishida, Lodkaew, Yamane (2026)**
*CapBencher: Give Your LLM Benchmark a Built-in Alarm for Test-Set Overfitting*
[arXiv:2505.18102](https://arxiv.org/abs/2505.18102) — **ICML 2026 camera-ready**

### 3.1 ⚠️ 更正一处记忆错误

**我之前一直叫它 PhishBencher，正式名是 CapBencher。写论文时不能弄错。**

### 3.2 它的做法（对我们的多解随机化有用）

> "reducing the best possible accuracy, i.e., Bayes accuracy, by injecting randomness to the answers by preparing **several logically correct answers**, and only include **one of them** as the solution."

**⭐ 关键点：它要的是「几个逻辑上都对的答案」，随机公布一个。**

**所以它和我们不冲突 —— 它需要多解，我们需要唯一解，看似矛盾。解决办法在下面第四节。**

---

## 四、⚠️ 两篇放一起看，暴露一个真矛盾

```
ReverseMath   要求：唯一可解（一条路径）
CapBencher    要求：多个逻辑正确解（多条路径）

我们的设计同时用了这两个
```

### 4.1 矛盾在哪

**Frank 的规则里有两句话：**

> ① 「构造 12 个唯一解，固定头尾，中间差十个运算过程」
> ② 「每十个连续选项中正确选项不能超过三个」

**如果「12 个唯一解」是字面意思（12 条都能到终点的合法路径），那题目就不唯一，与 ReverseMath 冲突。**

### 4.2 我的判断：这 12 个不是「12 条路径」

**看 Frank 的原话上下文：**

> 「先生成十个指派解，然后构造四十个无关变量」
> 「固定头尾，中间差十个运算过程，然后塞四十个无关项」

**40 个无关项 + 10 步过程 = 50 个选项。所以：**

```
50 选项 = 10 个正确项（路径上的 10 步）+ 40 个无关项
```

**「12」更可能是选项总数或某种留余量，而不是 12 条独立路径。**

**⚠️ 这条我判断不准，需要 Frank 定。下面第四节给三个方案。**

## 六、⭐ 我们要改的四件事

### 6.1 唯一性检查改成「事后验证具体路径」

**不再问「函数集有没有等价合成」，改问「这条路径有没有第二条解」。**

```
方法：从起点出发做受限 BFS，深度 ≤ 步数，只走比终点更短的路径
      撞到任何节点就剪枝（防止中间值重复）
      如果除已知路径外还能到终点 → 有多解 → 拒绝
```

**这是 ReverseMath 的 `uniquely solvable` 检查，也是唯一真正相关的检查。**

### 6.2 终点范围改成相对量级

**现在：`end ≤ 1000 × 11 = 11000`（绝对数，必然失败）**

**改成：**

```
|end| ≤ start × max_growth
或者：限制每一步的增长率，保证 |end| 与 |start| 同数量级
```

**这是真正的瓶颈（133/200 = 66.5%）。**

### 6.3 `make_op_pool` 的 bound 参数要真生效

**现在 `bound=7` 写死在函数里，`pool_size=4000` 根本取不到 → 池子永远 ≤ 210。**

**改成：bound 由池子目标大小反推。**

### 6.4 `disconnected_at` 的注释和代码方向相反

**注释说「作用后落在已知节点 = 接得上 → 返回 False」，代码是 `if op.apply(x) in fs: return False`（返回「接不上」）。**

**⚠️ 语义要统一，这条我先标出来，改的时候确认。**
