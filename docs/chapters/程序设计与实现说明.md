## 一、这一套程序在做什么

**一句话：把「函数复合」变成可出题的结构，并保证正算与反算严格成对。**

具体说，给定 k 个数学函数排成一条链，程序负责：

```
① 造一条链         y → f₁ → f₂ → … → f_k → x
② 每步定一个系数   让中间值落进下一步能吃进去的范围
③ 记住每步的系数   正向乘，反向就除同一个数
④ 检验反推唯一性   反推回来必须还是原来那个 y
⑤ 写成题面        文本 / 符号 / 文字叙述，可注入文本框
```

**⭐ 核心约束只有一条：每一步的系数，正向和反向必须是同一个数。**

这条约束贯穿全部设计，后面每一节都是它的推论。

## 二、数理包：把「算」和「写」分开

### 2.1 三层结构

```
registry.py   原料层   74 个函数：正运算、逆运算、搜索区间、值域
mathpack.py   计算层   把「f + f⁻¹ + c」绑成一个不可拆的整体（MathPack）
skeleton.py   书写层   每个函数怎么写得出来（LaTeX / ASCII / 中文）
```

**⭐ 为什么分三层：**

- **原料层**只管数学，不管题面
- **计算层**只管算得对不对
- **书写层**只管写不写得出来

**⚠️ 这三层之间不共享状态。** 计算层拿不到书写层的东西，书写层也不碰计算。

### 2.2 数理包（MathPack）

一个数理包是一个**整体**，包含三样东西：

| 成分 | 含义 |
|---|---|
| `f` | 正运算 |
| `f⁻¹` | 逆运算 |
| `c` | 打包时定死的系数 |

**⭐ 三者不可分离的理由：**

- 没有 `f⁻¹` → 解不出来，选项无法验算
- 没有 `c` → 分不清「y」和「x」，数量关系会错

**⚠️ 关键设计：`c` 打包时定死，正逆共用同一个值。**

早期实现把系数挂在工具上、运行时现算，结果：**正向按 `y` 算出 `c=10`，反向按 `x` 算出 `c=100`，两边不抵消反而叠加。** 实测回验误差 90%~100%。改成打包定死之后，全部降到 1e-16 量级。

### 2.3 核心恒等式

```
已知：   c · f(y) = x
两边同除 c：

         f(y) = x / c

反解：

         y = f⁻¹(x / c)
```

**⭐ 「成对」的真正含义不是「两边各算一次 c」，而是「两边共用同一个 c」。**

## 三、嵌套：k 步复合怎么走

### 3.1 链

一条 k 步的链：

```
第1层  t₁ = f₁(y) · c
第2层  t₂ = f₂(t₁) · cn₁
…
第k层  x  = f_k(t_{k-1}) · cn_{k-1}
```

**⭐ 每一层的输出既是「上一层的答案」，又是「下一层的输入」。**

### 3.2 每一层要解决的两个问题

**问题一：量级。**

上一层输出的量级可能和下一层能接受的范围差很多。
比如 `sqrt` 输出 0.1~9.8，而 `ellipk` 只接受 `(0.01, 0.98)`。

**问题二：符号。**

上一层输出可能是负的，而下一层只收正数。
实测：59 个可进链的包里，**42 个只收正数**。

### 3.3 系数 cn 的规则

**cn 逐样本、逐层现算**，不打包时定死。

**⭐ 三层规则：**

| 情形 | 取值 |
|---|---|
| 值在目标区间内 | `cn = ±10^k`，k 取整数，把它拉到区间里 |
| 值在区间外 | `cn = ±10^k`，k 取整数，先拉回来 |
| 无合适值 | 保持 `cn=1`，由验算判这一步不通过 |

**⭐ cn 允许带负号** —— 负输出乘 −1 就翻成正的，解决符号问题。

**⚠️ 为什么不用连续指数（`10^n`，n 取实数）：**

实测对比（每档 40 条随机链）：

| k | 整数 cn | 连续 cn |
|---|---|---|
| 3 | **100%** | 88% |
| 8 | **100%** | 90% |
| 10 | 90% | **92%** |

**平均反而更低**，而且题面会变成 `0.0217893x = f(y)` 这种非十进制精确的数。**已回退为整数。**

### 3.4 逐样本独立

**⭐ 十个选项 = 十条独立路径。**

```
选项 n:  y_n → x_{n,1} → x_{n,2} → … → x_{n,k}
```

**⚠️ 系数必须逐样本独立。** 实测：一批样本共用一个 cn 时，样本越多跨度越大：

| 样本数 | 第2层跨度 | 能否塞进 |
|---|---|---|
| 1 | 1.0 倍 | ✅ |
| **10** | **435 倍** | ✅ |
| **20** | **440 倍** | ❌ |

**n=10 勉强过，n=20 就崩。** 一个乘数只能整体平移，压不了跨度。

### 3.5 系数表

**⭐ 系数按 `(层, 样本)` 索引：**

```
cm[k, n]  = 第 n 个选项 · 第 k 层的系数
```

正向按层填，反向**查同一张表**。

## 四、反缩放：反向怎么把系数消掉

### 4.1 核心规则

**正向一步是两个乘法，反向就得两个除法：**

```
正向：  raw = f(t) · c        ← 包系数（打包定死）
        t'  = raw · cn        ← 本步系数（现算）

反向：  t   = f⁻¹(t' / cn / c)    ← 两个都要除
```

**⚠️ 漏掉任何一个都会崩。** 实测：`pow4` 的 `c=100`，只除 `cn` 不除 `c` 时，
每步验算全部通过（层内只验 `out/cn == raw`，管不到 `c`），
**但整链往返 0/200。**

### 4.2 符号怎么还原

`cn` 带负号时，反向除以负数会把符号自动翻回来。

**实测五条**（正向负输出、下一层只收正）：

```
betaln  −1.069  → beta       cn = −1  → 落进 [0.01, 20]  ✅
logit   −2.170  → exprel     cn = −1  → 落进 [0.01, 9]   ✅
erf     −0.269  → kve        cn = −1  → 落进 [0.05, 20]  ✅
log2    −4.317  → gammaincc  cn = −1  → 落进 [0.01, 20]  ✅
ndtri   −1.028  → cosh       cn = −1  → 落进 [0.01, 6]   ✅
```

**成对误差全部 0.0e+00。**

### 4.3 反推唯一性：判 x′==x，不是 y′==y

**⭐ 这两件事不一样。**

`f(f⁻¹(t)) == t` 只能说明反算没算错，**不能说明反推回来的是原来那个 `y`**。

例：

```
cos(y) = 0.3431
    y = 0.3431  ✓
    y = −0.3431 ✓
    y = 6.9399  ✓
    …无穷多个
```

**出题时 `y` 是标准答案。** 如果反推回来的是另一个根，做题的人算对了也对不上答案。

**判定四类：**

| 判定 | 条件 | 含义 |
|---|---|---|
| EXACT | 相对误差 < 1e-9 | 反推回原值 ✅ |
| NEAR | < 1e-5 | 精度所限，不是多根 |
| SAME_F | 值对但 x 换了 | **真多根** ❌ |
| BROKEN | NaN 或值也对不上 | 坏了 ❌ |

**⭐ `x ≈ 0` 时不能用相对误差** —— `6e-17` 除以 `|x|≈0` 会爆成 `1e283`。

### 6.2 反函数表述算法

**⭐ 三条规则，缺一不可：**

| # | 规则 | 实现 |
|---|---|---|
| ① | 做什么 | 有逆名用逆名；没有用 `f⁻¹` |

```

**⚠️ 括号里的「K 指…」不能省** —— 没有它，`K⁻¹` 就没有指代对象。

### 6.3 中间变量命名

**⭐ 用 `k1, k2, k3 …`，首次出现给中文说明，之后只用字母。**

```
对 x 做以十为底的对数，求出 k1。
对 k1 做自然对数，求出 k2。
对 k2 做立方，求出 y。
（记号说明：k1 指 x 的以十为底的对数；k2 指 k1 的自然对数。）
```

**⭐ 中文只用来解决歧义，说明一次之后全部用字母。**

### 6.4 句式

**两种句式，同一道题内允许混用。**

```
句式 A：对 <输入> 做 <反函数>，求出 <产出>。
句式 B：设待求量为 w，解方程 <函数>(w) = <输入>，得到 <产出>。
```

**⭐ 混用是设计上允许的。** 理由：需要加入随机性，**不能让模型形成固定范式**。

**⚠️ 但「没有歧义」是硬底线。** 已做过的检查：

## 七、随机性的来源

**⭐ 论文要写「可复现」，必须交代随机从哪里来、怎么记。**

### 7.1 五处随机

| # | 随机的对象 | 怎么随 | 种子 |
|---|---|---|---|
| ① | **初始值 y** | 在实测可用窗口内取，跨数量级的用对数均匀 | 全局种子 |
| ② | **链的组成** | 从 59 个可进链的包里随机抽 k 个 | 全局种子 |
| ③ | **步数 k** | 默认 k=2；测试时可指定 | 显式参数 |
| ④ | **句式 A/B** | 按题号奇偶交替（可混用） | 题号决定 |
| ⑤ | **系数符号** | 由「能否落进下一层」决定，不是随机 | 确定性 |

**⭐ 关键：④ 虽然叫「交替」，但本质仍是确定性的** ——
给定题号就能算出用哪种句式。**真正的随机只在 ①②。**

### 7.2 窗口从哪来

**⚠️ 初始值 y 不能随便摇。** 摇到区间外，这条链必然崩。

**做法（`chain. feasible_y` / `anchor`）：** 不推导、不假设，
**在最外层包的值域里撒一批 y，真的跑一遍逆运算，能跑通的那一段才是可用窗口。**

**⭐ 为什么用实测不用推导：**
纸面推导已经写错过两次（一次把 x 区间当 y 区间，一次让上一步的输出被本步值域覆盖）。
**实测不会错。**

### 7.3 种子策略

**⚠️ 现状（如实写）：**

- 生成脚本用 `random.Random(固定种子)`，**可复现**
- `packs.py` 的自检种子用 `sum(ord(ch) for ch in p.code)`，**可复现**
- **但全局统一种子管理尚未实现** —— 每个脚本各自固定种子

**⭐ 论文中应写为「单次运行可复现」，不宜写「实验级完全可复现」**
（后者需要统一的种子注入机制，尚未实现）。

## 八、调度：CPU 与 GPU 怎么分工

### 8.1 设计意图（设计目标，**尚未完全实现**）

**⭐ 设计目标：CPU 负责决策，GPU 负责计算，中间只握一次手。**

```
CPU（一次）      ① 选算法、选链、定步数
                 ② 把整批任务打包交给 GPU
      ↓ ────── 握手 ────── ↓
GPU（全程）      ③ 所有函数的正算、反算、验算
                 ④ 每步的系数 cn 在 GPU 上现算
      ↑ ────── 握手 ────── ↑
CPU（一次）      ⑤ 取回结果
```

**⭐ 这样设计的目的：** 避免 CPU 与 GPU 之间反复来回 ——
每次来回都要同步、都要等，而 GPU 空转的时间就是浪费。

**⚠️ 现状态（必须如实写）：**

| 环节 | 状态 |
|---|---|
| GPU 全程计算 | ✅ **已实现**（`memguard.py` 串行分批，全部张量在 GPU 上算） |
| CPU 一次调度 | 🟠 **部分实现**（链由 Python 侧选定，但是**逐条串行**，没有批量打包） |
| 专门线程握手 | 🔴 **未实现**（当前靠 `torch.cuda.synchronize()` 隐式同步） |
| **CPU 多核并行** | 🔴 **未实现** |

**⚠️ 关于「四核八线程」：**

这是**设计时的最低配置目标** —— 让调度逻辑在 4 核 8 线程的机器上也能跑。
**当前代码里没有任何 CPU 多线程调度实现**（`threading` 只出现在
`gpu_monitor.py` 的采样监控线程里，与任务调度无关）。

**实测硬件（非最低配置）：**

```
CPU          16 逻辑核（8 核 16 线程）
GPU          NVIDIA RTX 5060 Ti，36 SM
显存         15.93 GB
CUDA         13.0 · torch 2.13.0+cu130
```

**⭐ 所以「四核八线程」目前是**设计约束**，不是**实现事实**。论文中应写为
「调度逻辑按 ≥4 核 8 线程的机器设计」，不能写「已在线程级实现并行」。

### 8.1.1 为什么没实现（留档）

**设计者对这块的判断（原话）：**

> 「当初改完之后没能跑起来，我估计是 CUDA 代码可能有什么潜在的格式。所以我写不进去。」

**⚠️ 此原因未经复现确认，此处只作留档。**
以后再动这块，**先查 CUDA 侧的编译与格式问题**，不要从头重写调度逻辑。

### 8.2 GPU 调度：串行分批（已实现且有实测）

**⭐ 为什么串行而不并发：** 串行不抢显存，逻辑简单，出错好查。

**实测（`gpu_bench.py`，RTX 5060 Ti）：**

| batch | ms/千项 | GPU 占用 | 显存 |
|---|---|---|---|
| 256 | 28.8 | 5% | 1.5 GB |
| 1024 | 7.2 | 5% | 1.6 GB |
| 4096 | 2.2 | 5% | 1.9 GB |
| 16384 | 1.15 | 5% | 2.9 GB |
| **65536** | **0.95** | 26% | 6.9 GB |
| **262144** | **5.89** | 100% | 15.6 GB |

**⭐ 结论：**

- 单个巨大 batch 会把显存吃满并触发抖动，**反而慢 6 倍**
- 每千项最快的是 **65536**
- 65536 单块只有 26% 占用 → 靠**串行跑多个块**把占用拉起来

**三个关键参数：**

```
BATCH_SIZE      = 65536     单块大小（实测每千项最快）
TARGET_UTIL     = 0.65      目标 GPU 占用
MEMORY_FRACTION = 0.75      显存硬上限（15.93 GB × 0.75 ≈ 11.9 GB）
```

### 8.3 显存管理

`set_per_process_memory_fraction(0.75)` 设进程级硬上限。

**⚠️ 实测：** 显存不是瓶颈 ——
B=512 峰值仅 0.11 GB，B=4096 峰值 0.87 GB。

**⭐ 真正的瓶颈是每次调用的固定开销，不是显存。**

### 8.4 为什么系数在 GPU 上现算

**⭐ 每步的系数 cn 依赖「这一步实际算出什么值」，只有算完才知道。**
所以必须在 GPU 上逐层现算，不能预先在 CPU 上定好。

**⚠️ 但这正是「CPU 一次调度」目标的部分落空之处：**
严格说，这是**逐层握手**而非一次握手。

**⭐ 这是设计目标与实现现状的差距，论文中应如实说明：**

> 设计上希望「CPU 只握手一次」，实际实现中每层的系数必须在该层算出结果后才能确定，
> 因此存在逐层同步。这一点在后续版本中可考虑用 GPU kernel 融合解决。

## 八之二、链的构造：从锚点起步

> **⚠️ 本章及以下三章（八之二至八之五）写于 2026-11-07。**
> **目的是让人**只凭本文档**就能重做一遍，不必去读源代码注释。**

### 8b.1 方向问题：从哪一头开始算

**⚠️ 这是全流程最容易搞错的地方，本文自己搞反过两次。**

**要造一条链，必须先回答：从起点算还是从终点算？**

```
❌ 看起来的做法（错的）：
   v₀ ──→ v₁ ──→ v₂ ──→ … ──→ v₁₀
   「从起点往外推」

✅ 实际的做法：
   v₀ ←── v₁ ←── v₂ ←── … ←── v₁₀
   「从最内层往里推」
```

**为什么必须从内往外：**

链的定义是 `v_{i+1} = fᵢ(vᵢ) · cnᵢ`。

- 若从 `v₀` 出发，**必须先知道 `cn₀`**，而 `cn₀` 取决于 `f₀(v₀)` 是多少，
  但 `f₀(v₀)` 的值域能不能接上下一步，取决于下一步要什么。
- **→ 成了一个循环。**

**做法改为先挑最内层的锚点，再逐层往外推。**

### 8b.2 四个基本函数

**这四个是链构造的全部原语。**（`anchor.py`）

| 函数 | 输入 | 输出 | 干什么 |
|---|---|---|---|
| `anchor_candidates` | 一个包 | 若干候选值 | 列出这个包**能接受的输入值** |
| `usable_anchor` | 包 + 一个值 | (能否用, f 值, 误差) | 判这个值能不能**正逆走通** |
| `fit_cn_to_next` | f 值 + 目标区间 | (cn, k) | 找系数让 `f·cn` **落进下一层** |
| `pick_anchor` | 包 + 下游需求 | 一个可用坐标 | 上面三个的组合，挑出一个 |

### 8b.3 `anchor_candidates`：候选值从哪来

**核心约束：只能用 `pack.search`（这个包真正能接受的输入）里的值。**

**⚠️ 为什么必须往区间内收 5%：**

```
搜索区间       [0.01, 100]
直接取端点     0.01        ← 在开区间边界上，f⁻¹ 可能不收敛
往里收 5%      5.0095      ← 安全
```

**实测教训（2026-11-07）：**
k=10 有一条链把 `pow8` 的输入推到 `0.011`（下界 `0.01`），
那里 `pow8` 的输出 `2.2e-14` 和其他点挤在一起，**反推不回来**。

**⭐ 根因不是算法错，是深链把值推到了定义域边缘，那里分辨率低。**

**默认给三个点：**

```
LO  = lo + span × 0.05           下界内收
HI  = hi − span × 0.05           上界内收
MID = 几何平均或算术平均          见下
```

**⚠️ MID 的算法有讲究：**

```python
if a > 0 and b / a > 100:
    MID = sqrt(a × b)       # 跨数量级 → 几何平均
else:
    MID = (a + b) / 2       # 否则 → 算术平均
```

**⭐ 为什么：**
区间 `[0.01, 100]` 的算术平均是 `50.005`，偏向高端；
几何平均是 `1`，真正在中部。**跨数量级时必须用几何平均。**

**⚠️ 2026-11-07 扩充：`n_extra` 参数**

**默认 `n_extra=0`，行为与之前完全一致。**

**为什么必须能扩充：**

```
pow2 的 search = (0.01, 100)
sqrt 的 search = (0.01, 100)     ← 完全一样

→ 两者的候选 LO 都是 5.0095
→ 链里同时出现，v₀ = v₂ 必然成立
→ 重试多少次结果都一样
```

**实测：200 条 k=10 的链，99% 因节点重复被淘汰，且 1.57 秒/条。**

**扩充后：在 `[a, b]` 内随机再取 `n_extra` 个点。**

```
同号且跨度 > 100：对数均匀  v = exp(uniform(log a, log b))
同号且跨度 ≤ 100：算术均匀  v = uniform(a, b)
跨零：          线性均匀，且避开 0 附近
```

### 8b.4 `usable_anchor`：一个值能不能用

**必须同时成立三件事：**

```
① f(v)·c 有限
② f⁻¹(f(v)·c / c) 有限       ← ⚠️ 先除包系数 c
③ f(f⁻¹(...))·c ≈ f(v)·c     ← 回来对得上
```

**⚠️ ② 那个「先除 c」是踩过坑的：**

```
pow4 的 c = 100
x = 0.05995  →  f·c = 0.00129
_inv(0.00129) →  0.1896     应为 0.0599，相对误差 99
```

**漏了除 c，所有候选都判 `ok=False`，整条链「锚点挑不出来」。**

**⭐ 这条规则出现过三次**（`layerchain` 两处、`anchor` 一处）：

> **凡是正向乘了 `c` 的地方，反向就必须先除 `c`。**

### 8b.5 `fit_cn_to_next`：系数怎么定（本流程最关键的一处）

**目标：找一个 `cn = ±10^k`，使 `f · cn` 落进下一层的 `search` 区间。**

**⚠️ 第一版错了：不能对 `f` 取绝对值。**

```
tanh 输出 −0.9999
abs() 后当成 +0.9999
判成「能落进 [0.01, 0.98]」
实际上 ellipe 根本不吃负数       ← 整条链断在第 2 层
```

**⭐ `cn` 允许带负号（2026-11-07 定）：**

```
原来 cn 只能是 10^k（恒正）
→ 「负输出撞只收正的下游」必然断
→ 实测断了 5 条：betaln / logit / erf / log2 / ndtri
→ ✅ cn = −1 一乘全部接上，成对误差 0.0e+00
```

**搜索算法：**

```python
for k in range(0, 31):
    for mag in [10^k, 10^−k]（k=0 时只有一个）:
        for s in [+1, −1]:
            v = f · mag · s
            if 区间内: 记录
    if 找到了:  break        ← 找到最近量级就停
```

**⭐ 排序规则：先比量级（离 10⁰ 越近越好），同量级先试正号（题面更干净）。**

### 8b.6 ⚠️ 连续系数：试过、测过、回退了

**方案**：`cn = ±10^n`，`n` 取实数，可连续微调。

**实测对比（每档 40 条随机链）：**

| k | 整数 cn | 连续 cn |
|---|---|---|
| 2 | 100% | 100% |
| 3 | 100% | **88%** ↓ |
| 4 | 100% | 100% |
| 5 | 98% | **92%** ↓ |
| 6 | 98% | 98% |
| 8 | 100% | **90%** ↓ |
| 10 | 90% | 92% ↑ |

**平均下降，而且题面变丑：**

```
整数：  0.1x = f(y)             ← 干净
连续：  0.0217893x = f(y)       ← 成了带舍入误差的任意实数
```

**⭐ 结论：负号是决定性的（k=8 从 38%→92%，正向断彻底消失），
连续微调收益不稳定还牺牲题面 —— 所以只用整数。**

**⚠️ 还有一处失败：「推到区间中心」反而更差**（k=10 从 90%→75%）。
**说明中部未必好，有些函数在中部反而不易解。**

**⚠️ 连续版代码留在 `history/20261107_退役/contcoef.py`，不启用。**

### 8b.7 `pick_anchor` 与整链规划

**`pick_anchor` 做的事：**

```
① 取 anchor_candidates 的全部候选
② 逐个跑 usable_anchor，筛出能用的
③ 若有下游需求 want，再筛「乘 cn 后能落进 want」的
④ 按 prefer 排序
⑤ 取结果
```

**⚠️ 默认 `n_extra=0` 时恒取第一个（与之前完全一致）。**
**`n_extra>0` 时在合格候选里随机取 —— 这是撞车能避开的机制。**

**整链规划 `plan_anchors` 的流程：**

```
for 每一层 i（从最内层往外）:
    if i == 0:
        自己挑锚点（要看下一层 want 什么）
    else:
        输入已被上一层定死，只验证能不能用
    定这一层的 cn：
        若有下一层 → 落进下一层的 search
        若已是最后一层 → 落进自己的 y_range
    校验：真的落进去了吗（带符号判，不取绝对值）
```

**⚠️ 最后一层的目标区间是 `p.y_range`（自己的值域），不是下一层的 search。**

**⭐ 这一条搞错过：把「下一层能接受的输入」当成了「下一层的输出范围」。**
**这两个区间语义完全不同，弄混会导致 NaN 级联。**

## 八之三、向量化：为什么能并行、怎么分组

### 8c.1 为什么必须批量

**实测（单个包，同一函数）：**

| 一次算几个值 | 每个值耗时 |
|---|---|
| 1 | **1437.950 us** |
| 1000 | 0.027 us |
| 10000 | 0.003 us |
| 100000 | 0.003 us |

**⭐ 批量 1000 个，每个值快 5 万倍。**

**根因：GPU 的启动开销是固定的（约 1.4 ms）。
一次算 1 个值，这 1.4 ms 全花在等上；一次算 1000 个，等于摊薄了。**

### 8c.2 什么能并行、什么不能

**这是本章最重要的一句话：**

```
层与层之间  →  必须串行
    因为 v_{i+1} 依赖 f_i(v_i)，算不完这层就不知道下一层输入

不同链之间  →  完全独立
    链 A 的第 3 层和链 B 的第 3 层没有任何依赖
```

**→ 所以并行的是「不同的链」，不是「同一条链的不同层」。**

**示意图：**

```
      链A      链B      链C
层1   v1_A     v1_B     v1_C     ← 一次 GPU 调用
       ↓        ↓        ↓
层2   v2_A     v2_B     v2_C     ← 一次 GPU 调用
       ↓        ↓        ↓
层3   v3_A     v3_B     v3_C     ← 一次 GPU 调用
```

**⭐ 10 层 = 10 次 GPU 调用，不管同时跑多少条链。**

### 8c.3 ⚠️ 分组：为什么不能一次算全部

**问题：同一层上，不同链用的包可能不同。**

```
第 3 层用的包：
  链A → pow8
  链B → erf
  链C → pow8      ← 和 A 一样
  链D → log_ndtr
```

**→ 不能把所有链的输入拼成一个张量，因为 `pow8` 和 `erf` 是不同的函数。**

**做法：按包名分组。**

```python
groups = {}
for 每条活着的链 i:
    groups[链i这一层的包名].append(i)

for 包名, 链列表 in groups.items():
    sel = 取这些链的当前值
    f   = 该包._fwd(sel)        ← 一次调用算完这一组
```

### 8c.4 ⚠️ 分组的代价（论文要写这一段）

**若 M 条链、每层有 G 种不同的包，则每层需要 G 次调用。**

```
M=4096，每层最多 59 种包（可用包数）
→ 最坏情况每层 59 次调用
→ 10 层 = 590 次调用
→ 每次约 1.4 ms → 约 0.83 秒
```

**但实测 M=4096 只要 0.94 秒** —— **说明实际分组数远小于 59。**

**原因：**
- 每层用的包是从 59 个里**随机抽**的，M=4096 时几乎每个包都会被用到
- 但**大量链在早期就被淘汰**（量级越界、进不了下一层），层数越深，活着的链越少
- 深层的组内条数下降，但组数也下降 → 摊薄效应仍在

**⚠️ 论文里应如实写出这个代价，不能只说「快 5 万倍」。**

### 8c.5 ⚠️ 边界情况：某组只有 1 条链

**这是分组方案的固有弱点。**

```
若某一层某个包里只有 1 条链活着
→ 这次 GPU 调用只算 1 个值
→ 1.4 ms 全浪费，等于退回串行
```

**实测数据说明了这个代价有多大：**

| 批量 M | 耗时/题 |
|---|---|
| 64 | 25.19 ms |
| 1024 | 1.96 ms |
| 4096 | 0.94 ms |
| 16384 | 0.42 ms |

**⭐ M 越大，每个值越便宜 —— 因为「只有 1 条链的组」占比越来越小。**

**⚠️ 所以 M 不能太小。论文里用 M = n × oversample（默认 1.3 倍）计算单批规模。**

### 8c.6 实现要点：整条链留在 GPU 上

**`gen_chains_batch` 的做法：**

```
① 起点：一次性搬到 GPU，形状 (M, k+1)，初值 NaN
② 逐层循环，每层只更新活着的那些
③ 终值：在 GPU 上连乘
④ 只在最后把结果搬回 CPU 一次
```

**⚠️ 关键：中间不搬回 CPU。**

**若每层都 `.cpu()`，PCIe 传输会把批量的收益全部吃掉。**
**实测：显存占用很小（32768 条远低于 15.93 GB 上限）。**

## 八之四、数值层：干扰值怎么造

### 8d.1 为什么干扰值必须"看起来像真的"

**⚠️ 这里有一个极易被忽略的泄露点，本文第一版就踩了：**

```
正确项：3–6 位有效数字   （1.2341、3.14159、271.828）
无关项：15–17 位        （-362.1381842、0.02151967954）
```

**→ 看小数位数就能认出答案，题目等于无效。**

**实测确认：**

```
正确项有效位数：[3, 4, 5, 5, 5, 5, 5, 6, 6, 6]
无关项有效位数：[15, 15, ..., 17, 17]         ← 完全分离
```

**⭐ 修法：干扰值按正确项的有效位数取整。**

**数量级也会泄露答案**，所以取值域必须覆盖正确项所在的量级。

### 8d.2 `make_decoys_gpu` 的算法

**输入**：`avoid` —— 形状 `(M, k+1)`，每条链的 11 个节点值
**输出**：形状 `(M, n_decoy)` 的干扰值

**逐列生成（共 `n_decoy` 列）：**

```
对每一列 d：
    ① 随机取量级：lg = uniform(lo_log, hi_log)，mag = 10^lg
    ② 随机定符号：sign = ±1（各 50%）
    ③ v = mag × sign
    ④ 检查是否与「节点」「已造出的干扰值」相碰（相对误差 ≤ tol → 算碰）
    ⑤ 碰了的重新抽，最多 40 轮
```

**⭐ 取值域怎么定：**

```
基准：由本批节点的量级决定
    lo_log = log10(min|节点|) − 2
    hi_log = log10(max|节点|) + 2

⚠️ 再与配置给的 [decoy_lo, decoy_hi] 取交集
    → 防止干扰值跑到荒唐量级（那样一眼就假）
```

**⚠️ 取交集这一步是必须的：单靠节点量级可能过宽，
单靠配置可能过窄（盖不住节点）。两者取交集才安全。**

### 8d.3 "相碰"的判据：相对误差

**两个数 `a` 和 `b` 算不算同一个：**

```
|a − b| / max(|a|, |b|) ≤ tol   →   算碰
```

**⚠️ 为什么用相对误差而不是绝对：**

数值跨度可以到 `1e-30` 到 `1e30`。**绝对误差在两端都没意义。**
`1e-30` 和 `1.001e-30` 的绝对差是 `1e-33`，看起来极小，但**对模型来说是两个完全不同的数**。

**⚠️ `tol` 的取值有一个易错点：**

```
make_decoys_gpu 的函数默认 tol = 1e-9
但 build_vector_problems 实际调用时传的是 delta_opt（默认 1e-6）
```

**⭐ 实际生效的是 `delta_opt`，不是函数默认值。**

**为什么必须传：**
干扰值要和**选项**有同样的区分度。若判碰用 `1e-9`，
会造出一个和正确项只差 `1e-7` 的干扰值——**模型分不清，但系统认为"不碰"。**

**⚠️ 所以直接调用 `make_decoys_gpu` 时必须显式传 `tol`，不能依赖默认值。**

### 8d.4 ⚠️ 干扰值不参与"正确答案"的判定

**干扰值的唯一作用是：**
```
让模型不能靠"排除法"直接筛出正确答案
```

**它们不影响唯一性判定** —— 唯一性看的是**链上 11 个节点**是否两两不同，
与干扰值无关。

## 八之五、选项、工具与总装

### 8e.1 三层数据的关系（回顾）

```
第 1 层 库存：  k 个中间值 + n_decoy 个干扰值 = k+n_decoy 个值
                       ↓                  ↓
第 2 层 选项：  k + n_pick          （从 n_decoy 里抽 n_pick 个）
第 3 层 工具：  k + n_decoy         （全部库存）

默认：k=10, n_decoy=50, n_pick=40
      → 库存 60，选项 50（10+40），工具 60
```

### 8e.2 `pick_options_gpu`：选项怎么组

```
① 从 n_decoy 列干扰值里随机抽 n_pick 列（用 argsort(rand) 取前 n_pick）
② 拼成 (M, k + n_pick)：前 k 列是中间值，后 n_pick 列是抽中的干扰
③ 同时生成「步数标记」：中间值标 1..k，干扰标 0
④ 打乱：对整个 (M, 50) 各行的顺序随机置换
⑤ 值和步数标记同步打乱
```

**⭐ 为什么要保留「步数标记」：**
判定时要回答「你选的是不是链上第 3 个值」，
**光有值不够，必须知道它对应链上第几步。**

### 8e.3 `build_tools_gpu`：工具怎么组

**Frank 的原话：**
> 「这工具是从 10+50 直接的随机变化里来。」

```
① 把中间值 (M,k) 和干扰值 (M,n_decoy) 拼成 (M, k+n_decoy)
② 角色标记：中间值 = 1..k，干扰 = 0
③ 对每一行做随机置换，取前 n_tool 个（n_tool = k + n_decoy，即全取）
④ 每条工具体现在是：{值, 步数, 是否在链上}
```

**⚠️ 当前实现「只标记、不生成抽象层」：**

**工具池里的每个条目目前只有三个字段，还没有做「抽象」（如多语言命名替换、描述模糊化）。**
**那一层在 `skeleton.py` / `narrator.py` 里，尚未接入 `vectorform`。**

### 8e.4 ⭐ `build_vector_problems` 总装：六道筛，顺序有讲究

**⚠️ 顺序不是随便排的 —— 便宜的在前，贵的在后。**

```
① alive         链本身可不可行（正逆没断）
② fin_ok        11 个节点是否都是有限值
③ mag_ok        每个 |v| ∈ [node_min, node_max]
④ uniq          两两相对误差 > δ_opt
⑤ final_ok      |v₁₁| ∈ [final_min, final_max]
──── 以下在 CPU 上逐条做（较贵） ────
⑥ 终值区分度    换掉一个中间值后，终值是否仍够远
```

**⭐ 为什么 ①②③④⑤ 都在 GPU 上批处理，只有 ⑥ 在 CPU：**

```
前五道都是「逐元素的布尔判断」→ 天然向量化
第六道要「换掉一位再全乘一遍」→ 每条要对 k 个位置各算一次
                              → 但只对选中的 n 道做，量小
```

**⚠️ `oversample` 的作用：**

**因为 ⑥ 会淘汰一些，所以要多造一些。**
**默认 `oversample=1.3`，即造 130 条来取 100 道。**

### 8e.5 ⭐ `_nearest_alt`：为什么挑最接近的干扰值

**这是 ⑥ 的关键，**也是本文最容易被问倒的一处。**

```python
alt = _nearest_alt(decoys, mid, pos, mid[pos])
```

**它的作用：从干扰值里找**与当前位置的值最接近**的那个。**

**⚠️ 为什么必须挑最近的：**

```
随便挑一个很远的干扰值 → 终值一定差得远 → 测不出问题
挑最近的              → 这是最坏情况 → 才能证明"换任何一个都安全"
```

**⭐ 判据逻辑：**

```
若「最接近的那个替换后」终值仍然够远
→ 那么「任何更远的」替换后必然更远
→ 覆盖面得证
```

### 8e.6 UID 与哈希链

**`make_uid(seed, chain, idx)`：**

```python
raw = f"{seed}|{','.join(chain)}|{idx}"
uid  = sha256(raw).hexdigest()[:16]
```

**⚠️ 为什么不用 Python 内置 `hash()`：**

**`hash()` 每个进程不同（有随机化盐），同一份数据跑两次得到不同的值。**
**这个坑本文踩过**（`packs.py` 的自检种子用它，导致三次跑出三个数字）。

**`hash_link(prev, uid)`：**

```python
link = sha256(f"{prev or 'GENESIS'}->{uid}").hexdigest()[:16]
```

**作用：把题目序列串成链。**

**实测：篡改任意一个 UID，后续所有 link 全部对不上 → 可检测。**

### 8e.7 可复现性的三个保证

| 层 | 保证方式 |
|---|---|
| **UID** | 由 `seed + chain + idx` 算出，不含时间、不含随机 |
| **选项/工具** | 每个子步骤用 `seed + 固定偏移` 建 GPU generator |
| **哈希链** | 由 UID 顺序推出，不含随机 |

**实测：同一 seed 两次运行，UID、link、digest 全部相同。**

**⚠️ 但要注意：`config` 的任何一项变化都会改变 UID**（因为 chain 变了）。
**所以配置必须写进日志。**

### 8f.1 为什么用初等与高等数学工具作为载体

**① 选了什么、为什么选**

**AGI 的定位是通用。** 现成的 AI 测试已经在数学计算上做了大量工作，
覆盖到中小学水平。**若通用智能停在这个层面，它支撑不了 AGI 的定位** ——
进入化工、航天这类领域的实际工作，所需的数学超出中小学范围。

**因此本文的工具集取用真实科学计算函数库里在用的函数**（`numpy` / `scipy` 等），
而不是只取中小学习题里出现的形式。

**② 现有测试已经提供了什么基础**

数学计算是现有 AI 基准最成熟的一块（MATH、GSM8K、Khan 题库、OlympiadBench 等）。
**这部分不需要我们重建。**

**③ 我们怎么结合**

```
现有基础：中小学数学的计算能力测试
         （成熟、被广泛接受、有大量现成题库）
                ↓
新的需求：AGI 要能进入前沿科技与复杂场景
         （需要真实工具生态里的函数）
                ↓
本 文：   保留现有数学计算的地位，
         把工具集扩展到科学计算库中的真实函数
```

**⭐ 一句可以写进正文的话：**

> 本文不替换现有数学基准所测的内容，而是在其基础上，把工具集扩展到
> 通用场景实际会调用的函数上。

**④ 承认它会变，并指出哪部分可替换**

**⚠️ 这只是我们的预测，代表一种期望，未来可能变化。**

**正因为可能变化，工具集被设计成可替换的**：

| 可变的部分 | 怎么换 |
|---|---|
| 具体用哪些函数 | 改 `registry.py` 的原料表 |
| 初等/高等各占多少 | **本文不设比例**（理由见 §5.3.1） |
| 工具数量 | `config.k` 与 `config.n_decoy` |

**⚠️ 固定的是框架与判据，不是具体函数清单。**

**⚠️ 表述纪律（与 §5.3.1 一致）：**

> 本文的工具集取自真实科学计算函数库，
> **但不按学科比例分配，亦不声称穷尽覆盖任何领域的工具。**

**⭐ 本文的主张是：若一套工具集能在这些真实工具上稳定出题并可判定，
那么它具备扩展的基础；本文不主张当前清单已经足够。**

### 8f.1b ⭐ 难度是多维的：本文为何选择"均衡的较低难度"

> **本节记录 Frank 2026-11-07 的完整表述，并整理为学术表述。**

**① 工具的选择本身就是一次难度取舍**

**本文的工具集不是"能选的都选"，而是多维筛选后的结果。**

**筛选的首要维度是**可计算性**：**

```
输出为标量，可直接参与后续运算        →  保留
输出为区间、向量、矩阵等非标量结构    →  排除
```

**⚠️ 这不是因为区间、向量、矩阵不重要，而是因为它们不适合本文当前的题目形式。**

**⭐ Frank 的原话（这句话点明了性质）：**

> 「这块也是为了测准入而降低难度，全上难度就应该把向量矩阵和区间全部作为 x 的值让 LLM 往回推。」

**② 难度的构成是多维的**

**本文不追求任何单一维度的极限，而是让各维度难度保持相对均衡。**
**当前设定落在较基础的区间。**

**具体表现如下表：**

| 维度 | 当前设定 | 可提升空间 |
|---|---|---|
| **高等函数** | 只给**单个值**用于推演 | 可要求系统自行在区间内定位 |
| **工具完整性** | **给出全部工具选项** | 可只给部分工具，要求系统自行补足计算 |
| **运算结构** | **仅在 y 值之间使用乘法** | 可在预指派链间复合嵌套更复杂函数 |
| **抽象层** | **仅中英两种语言 + 图片** | 可加入音频、视频、传感器数据、逻辑判断推理题 |
| **取值范围** | 标量 | 可引入区间、向量、矩阵 |

**③ 抽象层可扩展的具体方向**

**当前抽象层覆盖：**

```
中 / 英 双语   ·   图像表征   ·   随机词替换（变量名与工具名）
```

**可扩展方向：**

| 新增模态 | 测什么 |
|---|---|
| **音频** | 从听觉特征还原数学结构 |
| **视频** | 从时序变化中识别不变结构 |
| **传感器数据** | 从噪声信号中提取有效量 |
| **逻辑判断推理题** | 从规则描述还原目标结构 |

**⭐ 这些扩展的共同目的（Frank 原话）：**

> 「让大模型根据不同特征自己推断抽象的特征表达的是什么含义。」

**⭐ 换一个说法：** 无论表象如何变化，模型都应当能识别出同一个数学内核。
这正是 §八之六 全篇反复出现的「抽象能力」的具体形态。

**④ 本测试的定位（关键表态）**

**⚠️ 以下两句应与 §8f.7、§8f.8 一起读，它们共同构成本文的难度立场：**

> **本测试目前的难度设定较为基础，未来可提升的空间较大、方向较多。**
>
> **本基准测试仅为验证论证逻辑，以及提供一种验证 AGI 能力的基准测试设计思路。**

**⭐ 换句话说：本文交付的是**设计思路与可执行的框架**，
而不是一个"足够难"的基准。难度的上限由框架允许，
具体的难度档位是本文给出的一个可用起点。**

**⚠️ 表述纪律：**

| ❌ 不写 | ✅ 写 |
|---|---|
| 「本基准难度不足」 | 「本基准当前难度较为基础，可提升空间较大」 |
| 「我们故意做简单了」 | 「难度是多维的，本文选择均衡的基础设定」 |
| 「以后会做难的」 | 「框架允许在上述各维度上提高难度」 |

### 8f.1c ⭐ 随机性与种子库：如何防止模型"猜对"

> **本节回答一个会被反复追问的问题：既然所有题目都是程序生成的，模型能否靠猜测或记忆通过？**

**① 所有题目特征均可随机生成**

**本文的每一道题，其表层特征都不是固定的：**

| 可随机的对象 | 随机范围 |
|---|---|
| **工具**（函数） | 从可逆函数池中随机抽取 |
| **链长与结构** | 由 `config.k` 决定，各层函数随机组合 |
| **节点值** | 由锚点与系数逐层算出，随种子变化 |
| **干扰值** | 随机生成，且与所有节点保持区分度 |
| **选项顺序** | **每次随机置换** |
| **工具呈现顺序** | **每次随机置换** |
| **变量名 / 工具名** | 从词库中随机取词替换 |
| **语言** | 中 / 英（可扩展至联合国六种正式语文） |
| **图像表征** | 由结构生成，随参数变化 |

**② 种子库设计为可更改**

**⚠️ 本文的随机性不是写死在代码里的，而是从一个可替换的"种子库"中取用的。**

| 种子库 | 内容 | 可否替换 |
|---|---|---|
| **语言词库** | 中 / 英动名词表 | ✅ 可扩展至其他语种 |
| **抽象层素材库** | 图像表征模板 | ✅ 可加入音频、视频等 |
| **数学种子库** | 函数集与参数表 | ✅ **随函数集变化调整** |

**⭐ 这一点的方法论意义：**

> **若随机源可替换，则基准不会因为某一套词表被模型记住而失效。**
> 词库更新后，同一数学结构会以全新的表层形式重现。

**③ 选项顺序随机化：防的是"位置偏好"**

**⚠️ 这是一类容易被忽略、但确实会污染成绩的偏差：**

```
若正确选项总是集中在某些位置
→ 模型可能学到"选第 3 个"这类与能力无关的策略
→ 成绩不再反映能力
```

**本文的处理：**

```
① 选项值随机置换（值与步数标记同步打乱）
② 工具呈现顺序随机置换
③ 正确项在 50 个选项中的位置分布，不施加任何人工约束
```

**④ 与 §8f.8 的关系**

**本节是 §8f.8「最小化随机概率影响」的具体实现。**

```
§8f.8 提出原则：最小化随机影响，不最大化难度
        ↓
本节给出手段：表层全随机 + 种子库可换 + 顺序随机
        ↓
§8f.6 给出另一手段：精度可控（防浮点误差导致误判）
```

**⚠️ 但需要说明一个已验证的边界情况：**

**当前 `vectorform` 的实现中，选项顺序与工具顺序已经随机置换；
语言词库替换与图像生成尚未接入主流程**（见 §13.2 第 1、2 条）。
**因此本节的完整性依赖于后续接入。**

### 8f.2 为什么用预指派，并用它构造唯一解

**① 选了什么、为什么选**

**普通出题是「已知条件 → 算 → 答案」；本文反过来：答案先定，题目倒着造。**

**⭐ 这不是本文的发明。**「预指派」（pre-assignment）在学术界是正式术语：

| 文献 | 它用预指派做什么 |
|---|---|
| Horiyama et al. 2023, *Pre-assignment Models for Unique Vertex Cover* | **用预指派强制唯一解** |
| Zhao et al. 2026, *ReverseMath* | 答案确定性由构造保证 |
| Gima et al. 2025, *Forcing a unique MST and shortest path* | forcing set 强制唯一 |

**⭐ 本文与它们的对应关系：**

```
Horiyama：给它一个解 → 用预指派强制它是唯一解
本文：    给它一条链 → 避开所有别的中间值 → 强制只有这一条成立
```

**② 现有测试已经提供了什么基础**

现有数学基准出题是「条件 → 求答案」，**答案要算出来才知道对不对**。

**③ 我们怎么结合**

```
先指定答案 → 倒推出中间值 → 检查别的组合能不能也连成链
                                        ↓
                              不能 → 这条链是唯一的
                              （若不唯一 → 整条重造）
```

**⭐ 关键在「避开预指派值所有的中间值」：**

```
给定 10 个候选中间值 → 模型要找出能连成链的那一组
→ 只有一组（我们预指派的那组）
```

**这就是「用预指派构造唯一解」：本文的做法不是**碰巧**得到唯一解，
而是把唯一性**造出来**，再用筛选验证它确实唯一。**

**⚠️ 唯一性的两道保险：**

| 保险 | 检查什么 |
|---|---|
| **构造** | 预指派本身给出了一条确定成立的链 |
| **事后验证** | 11 个节点必须两两不同（`uniq` 筛，见 §8e.4） |

**⭐ 这与 ReverseMath 的立场一致：答案确定性交给构造，唯一性交给事后验证。**

**④ 承认它会变，并指出哪部分可替换**

**预指派不是唯一解的做法。** 任何能保证「答案先定、路径可验证」的构造方式都能达到目的。

**可替换的部分：**

| 可换 | 在哪 |
|---|---|
| 预指派的对象（指什么） | 本文指「答案 + 中间值」 |
| 构造的方式 | 本文用「指定 y，逆推 x」 |
| 唯一性的验证方式 | 本文用「两两不同 + 区分度」 |

### 8f.3 为什么加干扰项

**① 选了什么、为什么选**

**若只给正确的 10 个工具，模型只要能反推就能选对 —— 这测不出「在候选中做判断」的能力。**

**本文的做法：除了链上必需的 10 个工具，再加入 50 个干扰值对应的工具。**
（工具总数 = k + n_decoy = 10 + 50 = 60）

**② 现有测试已经提供了什么基础**

选择题是现有基准的常见形式，**但常规选择题的选项就是答案本身。**

**③ 我们怎么结合**

```
现有基础：有「在多选项中选一个」的形式
                ↓
新的需求：要测「识别工具功能」，不是「猜答案」
                ↓
本 文：   选项不是答案，是工具与中间值；
          模型交的是「工具集合 + 顺序」
```

**⭐ 干扰项的作用（一句话）：**

> 让模型不能靠排除法直接筛出正确答案，必须真的判断每个工具能不能接上。

**⚠️ 干扰项从哪来：**

```
本 文：  干扰值由同样的构造流程生成（预指派得出正确值后，
        另造 50 个与所有节点都不同的值）
```

**⚠️ 本文不用「编造的假函数」当干扰** —— 编造的一看就假，模型靠「没见过」就能排除，
那样等于没加干扰。

**④ 承认它会变，并指出哪部分可替换**

**干扰项数目是完全可调的：**

```
config.n_decoy = 50     # 干扰值个数
config.n_pick  = 40     # 其中几个进选项
```

**五个难度档把 n_decoy 从 20 调到 80**（L1 → L5，见 `D2026-11-07_配置体系.md` §五）。

**⚠️ 干扰项加多了有代价：**
工具数从 10 涨到 60，**模型上下文压力增加**；且干扰值可能与正确值撞车，
**这就是区分度 δ 的由来（见 §8f.8）。**

### 8f.4 为什么同时用正运算与反函数

**① 选了什么、为什么选**

**链上的每个函数都同时具备正运算 `f` 与逆运算 `f⁻¹`，且两者绑成一体（数理包）。**

**为什么必须成对：**

```
正向：  v_{i+1} = f(v_i) · c
反向：  v_i = f⁻¹(v_{i+1} / c)
                ↑ 用同一个 c
```

**⭐ 系数的正运算与逆运算必须共用同一个值，否则两者不抵消而互相叠加。**
（这是本文早期实现的真实错误，见 `D2026-11-06_计算架构换代与数理包重构.md` §一。）

**⭐ 双逆运算结构（本文的核心）：**

```
我方：  已知答案 → 【逆运算】 → 造出题目
模型：  拿到题目 → 【正运算】 → 找出路径

            我们的输入输出 = 他们的输出输入
```

**② 现有测试已经提供了什么基础**

现有数学基准测的是**正向求解**（给条件，求答案）。

**③ 我们怎么结合**

```
现有基础：测正向求解能力
                ↓
新的需求：要能验证「模型走的路是对的」，而不只是「答案碰对了」
                ↓
本 文：   反过来用逆运算造题，
          于是模型的正向过程每一步都可验证
```

**④ 承认它会变，并指出哪部分可替换**

**任何「正逆可验」的函数对都能用这个结构，本文取的是科学计算库里现成有逆函数的那些。**

**⚠️ 74 个原料里只有 59 个可逆**（`inverse_trusted=True`），
其余 15 个（`sin`、`cos`、`airy`、`jv`、`yv` 等）因**反推不唯一**被排除在链之外。

**可替换的部分：**

| 可换 | 怎么换 |
|---|---|
| 哪些函数入链 | 改 `registry.py` 的 `inverse_trusted` 标记 |
| 链长 | `config.k`（L1 到 L5 从 4 到 12） |

### 8f.5 为什么工具数量做成可调

**① 选了什么、为什么选**

**工具数量是一个可调参数，而不是固定值。**

**它的含义是：如果工具不给全，模型就必须自己做计算 —— 这要求更高。**

```
工具给全（含所有必需的）  →  模型只需识别并调用
工具不给全              →  模型还得自己补上缺失的计算
```

**② 现有测试已经提供了什么基础**

现有基准有一个隐含假设：**模型要么自己算，要么调用一个给定的工具。**

**③ 我们怎么结合**

```
现有基础：单一路径（自己算 / 调给定工具）
                ↓
新的需求：AGI 的分阶段定位 —— 准 AGI 阶段不应要求过高
                ↓
本 文：   工具数做成可调，
          对准 AGI 阶段不设那么高的准入要求，
          后续有需要可以升级难度
```

**⭐ 这一条要写进正文的一句话：**

> 本基准对准 AGI 阶段不设过高的准入要求。
> 工具数量是可调参数：若需要更高难度，可减少工具的完整性，
> 此时系统须自行补足计算。

**④ 承认它会变，并指出哪部分可替换**

**工具数 = `k + n_decoy`，是完全可调的因变量**（见 `D2026-11-07_配置体系.md` §3.4）：

| 预设 | k | 工具数 |
|---|---|---|
| L1 | 4 | 24 |
| L3 | 8 | 48 |
| **L4（默认）** | **10** | **60** |
| L5 | 12 | 92 |

**⚠️ 工具数不能单独设，它由 `k` 和 `n_decoy` 推出。**
**理由：若做成独立参数，会在工具池截断，可能截掉链上必需的工具，
造出「解不了题」的题而系统不报错。**

### 8f.6 为什么用系数放大（简写两点）

> **⚠️ 本条是代码实现层面的选择，不是设计意图，故简写。**
> **Frank 2026-11-07：「6.7是代码实现，不是设计意图，可以2点简写。」**

**① 保障尽可能多的被测函数与尽可能广的测试域**

各函数的输入区间量级差异极大（`tanh` 在 `(-5,5)`，`pow8` 的输出到 `8358`）。
**系数 `cn = ±10^k` 把上一层的输出拉进下一层的可接受区间**，
使**本来接不上的函数对能够接上**。

**② 同时把精度损失控制在浮点范围内**

**⚠️ 若缩放不当，中间过程会损失精度，使选项与答案间出现较大偏移，导致误判。**

**⚠️ 连续系数（`cn = ±10^n`，n 为实数）试过，已回退：**

| k | 整数 cn | 连续 cn |
|---|---|---|
| 3 | 100% | **88%** ↓ |
| 5 | 98% | **92%** ↓ |
| 8 | 100% | **90%** ↓ |

**平均反而下降，且题面变成 `0.0217893x = f(y)`，失去十进制精确表示。**

**⭐ 所以用整数 `k` 的 `±10^k`：负号解决「负输出撞只收正的下游」（k=8 从 38%→92%），
整数解决精度与题面。**

**⚠️ 可调的部分：** 系数形态本身（整数/连续）是代码层选择，
`history\20261107_退役\contcoef.py` 保留了连续版，需要时可接回。

### 8f.7 为什么用乘法把各层连起来

**① 选了什么、为什么选**

**本文用乘法把相邻节点连起来：**

```
v_{i+1} = f(v_i) · cn
```

**⭐ 这同样只是本文选的一种途径。**

**② 现有测试已经提供了什么基础**

预指派给出了一条确定性成立的链（见 §8f.2）；
**但要把这 10 段接起来，必须选定一种运算。**

**③ 我们怎么结合 —— 为什么是乘法**

| 理由 | 说明 |
|---|---|
| **量级可调** | 乘 `10^k` 能把输出从 `1e-5` 拉到 `1e2`，加法做不到 |
| **可逆且精确** | 除以同一个 `cn` 能精确还原（`10` 的整数幂在浮点里可精确表示） |
| **连乘终值是多因子结构** | 11 个节点连乘，任何一个变了终值都变 |

**⚠️ 加法不可行（本文实测过）：**

```
58.184 = v₀ + v₁ + … + v₁₀
从和值反推不出用哪 10 项 → 解不唯一
```

**④ ⚠️ 承认它可以更复杂，并说明本文的边界**

**预指派链之间可以复合嵌套更复杂的函数，那会大大增加破解难度。**

**但那不是本测试的内容。**

**⭐ 本基准测试的定位是验证模型的各项通用性维度指标，
不是在每一步上最大化难度。**

**⚠️ 一段可以直接写进正文的话：**

> 本文用乘法把预指派链的各段连起来，这是一种途径，不是唯一可行的途径。
> 在预指派链之间复合嵌套更复杂的函数可以提高破解难度，
> 但那超出本文的测试范围 ——
> **本基准旨在验证模型的通用性维度指标，而非在每一步上最大化难度。**
> 若后续需要提高难度，可采用更复杂的复合方式，框架本身不排斥这种做法。

### 8f.8 为什么最小化随机影响、而不最大化难度

**① 选了什么、为什么选**

**本文的设计取向是：尽可能小化随机概率的影响，而非在每一步最大化难度。**

**② 这两个目标为什么会冲突**

```
最大化难度      →  题目越来越刁钻
                →  但刁钻不等于测出通用性
                →  可能只测出「见过这类刁钻题」

最小化随机      →  题目可读、可复现、可判分
                →  模型的成绩反映能力而非运气
```

**③ 我们怎么结合 —— 具体的五道措施**

| # | 措施 | 防止的是什么 |
|---|---|---|
| 1 | **组合数 C(50,10) ≈ 1.03×10¹⁰** | 穷举 |
| 2 | **区分度 δ_opt / δ_final** | 多个组合都"接近"答案 |
| 3 | **11 个节点两两不同** | 中间值撞车导致多解 |
| 4 | **哈希链（UID + link）** | 题目被事后篡改 |
| 5 | **种子写进配置与日志** | 结果不可复现 |

**⭐ 第 2 条特别说明（Frank 2026-11-07 原话）：**

> 「不同答案之间要有区分度，不同选项之间也要有区分度，
> 不然的话，就很容易出现中间值四舍五入后乘起来，
> 有好几组满足答案的状况，其实这就是个乘法问题，
> 我们要限定每一步各个选项的精度差和最终答案的精度差，
> 而每个选项的精度差要为答案服务（受答案约束）。」

**落地为两条线：**

```
δ_opt   = 10^(−sep_digits)      选项之间
δ_final = δ_opt × √k            终值之间（k 段误差累加）
          ↑ 由 δ_opt 推出，不是另定的
```

**⭐「为答案服务（受答案约束）」的落地就是这条公式。**

**④ 承认它会变，并指出哪部分可替换**

**难度是可调参数，不是目的本身。**

| 可调 | 参数 |
|---|---|
| 组合数 | `config.k` + `config.n_pick` |
| 区分度 | `config.sep_digits`（默认 6，可 3 到 12） |
| 链长 | `config.k` |
| 工具数 | `k + n_decoy`（因变量） |

**⚠️ 防随机的措施（上述五条）不变，变的是难度。**

**有研究指出，选择题「无法捕捉开放式性质，且人为降低难度」**

## 八之六b、单条精造：`problem.py` 的算法（178 行）

> **⭐ 本节补写于 2026-11-07 晚。**
> **`vectorform.py` 是批量通路，`problem.py` 是单条通路 —— 它用于「指定一条链，造出一道题」。**
> **⚠️ 两者共用同一个造链原语（`anchor.verify_chain`），区别在于单条通路是串行重试，批量通路是并行推进。**

### 8fb.1 为什么还需要单条通路

**批量通路（`vectorform.build_vector_problems`）适合一次造几千道，但它有两个做不到的事：**

```
① 「我就想造这一条链」—— 批量通路只接受随机抽链
② 「这一条为什么不合格」—— 批量通路只回一个统计数，不说是哪一步断的
```

**⚠️ 所以单条通路是调试工具，也是复现工具。**

### 8fb.2 四个内层判据

**`build_problem` 内部定义了四个判据函数，按「便宜的先跑」排列：**

| 判据 | 检查什么 | 为什么放这个位置 |
|---|---|---|
| **`_final_of(nodes)`** | 算连乘终值 | 纯算术，最便宜 |
| **`_final_ok(f)`** | 终值 \|f\| 落在 `[final_min, final_max]` | 一次比较 |
| **`_nodes_ok(nodes)`** | 每个节点 \|v\| 落在 `[node_min, node_max]` | 11 次比较 |
| **`_running_product_ok(nodes)`** | 连乘积**逐步**检查，不越界 | ⚠️ 要用对数，见下 |

### 8fb.3 ⚠️ `_running_product_ok` 用对数，不直接相乘

**这是本条最容易写错的地方：**

```python
logabs = 0.0
for v in nodes:
    logabs += math.log10(abs(v))
    if logabs < log10(final_min) or logabs > log10(final_max):
        return False
```

**⚠️ 为什么不能写成 `prod *= v`：**

```
10 个节点连乘，量级可能到 1e-80 或 1e+80
浮点直接相乘 → 得到 0 或 inf
→ 之后既判不出「越界」，也算不出「差多少」
⭐ 对数累加没有这个问题：对数可以把 1e-80 到 1e+80 都压在一个有限的数上
```

**⭐ 更重要的：这不是只看最后一步，而是每一步都看。**
**因为中间某一步越界，即使最后又乘回来了，那条路径也已经不可靠。**

### 8fb.4 ⚠️ 前置检查：链上每个包必须可逆

**在造链之前，先查 `inverse_trusted`：**

```
若任一包的 inverse_trusted == False
→ 抛 ValueError，指出是哪个包
→ 不进入造链流程
```

**⚠️ 这一步不能省。** 实测踩过：
**`anchor.verify_chain(['sin','cos'])` 返回 `ok=False`（正确拒绝），
但 `trace_chain(avoid=True)` 会换多个种子重试，某一次碰巧误差合格，
就把不可逆的链放过去了。**

**→ 所以必须在最前面拦住，不能靠下游重试碰运气。**

### 8fb.5 两条路径：指定链 / 随机抽

```
若给了 names（指定链）：
    ① 前置查可逆
    ② trace_chain(avoid=True) 造链
    ③ 查唯一性（duplicate_pairs）
    ④ 查终值量级
    ⑤ 查节点量级
    ⑥ 查连乘积逐步
    → 任何一步不过，抛 ValueError 并说明是哪一步

若没给 names（随机抽）：
    循环 max_tries 次（默认 400）：
        ① 随机抽 k 个包
        ② 查可逆（不可逆就跳过重抽）
        ③ trace_chain(avoid=True) 造链
        ④ 五道判据依次过
        ⑤ 全过就返回
    → 超过 max_tries 抛 RuntimeError，附各类淘汰计数
```

**⚠️ 两条路径的关键差别：**

| | 指定链 | 随机抽 |
|---|---|---|
| 不合格时 | **抛异常**（因为这是用户指定的，不该默默换掉） | **跳过重抽** |
| 失败信息 | 明确指出哪一步不过 | 附各原因计数 |

### 8fb.6 ⚠️ 「撞车换锚点」而不是「整条重造」

**`trace_chain(avoid=True)` 的做法：**

**先用多个不同的锚点 seed 各试一次，取第一个「不撞车」的结果。**

```
for t in range(n_extra + 1):
    tr = _trace_once(names, n_extra, seed*1000 + t)
    if tr 不撞车: return tr
return None
```

**⭐ 为什么这样做：**

```
链本身是好的，只是某几个锚点值撞了
若整条重造 → 把好的部分也扔了，效率极低
换锚点     → 只换撞的那几个点，链结构保留
```

**⚠️ 实测价值：改成换锚点后，200 条 k=10 的链从「1% 可用」提到「96% 可用」。**

## 八之七、中间态：把一道题拆成可独立寻址的部件

> **⭐ 2026-11-07 下午新增。**
> **本章回答：造出来的题，怎么被拆开、怎么被打标记，好让后面能抽换。**

### 8g.1 为什么需要中间态

**造题（§八之三至八之五）产出的是一整块数据：链、节点、系数、选项、工具全混在 `VectorProblem` 里。**

**问题：**

```
想换掉某个函数的说法 → 得在整块数据里找它
想验证"换完之后数学没变" → 没有比对基准
想让模型看不同的表述 → 每处都得单独改
```

**⭐ 所以需要一层「中间态」：把每种部件抽出来，各自编号，各自打标记。**

### 8g.2 四类部件与编号规则
**Frank 的要求：**

> 「把变量和函数还有系数拆开来，同时打上独立代码和标记，
> 我的想法是，我们的中间量针对函数要识别出编号这是第几个编号函数，
> 这是独立于哈希值存在的，因为函数的抽象化可能要包含特征，每个函数不一样。」

| 类型 | 编号 | 数量 | 编号依据 |
|---|---|---|---|
| **变量 VAR** | `V000` – `V010` | 11 | 位置（链上第几个节点） |
| **函数 FUNC** | **`E001` / `H003`** | 10 | **复用 `packs.py` 已有的编号** |
| **系数 COEF** | `C00` – `C09` | 10 | 层号 |
| **选项 VALUE** | `N00` – `N49` | 50 | 呈现顺序 |

**⭐ 函数编号没有另造一套** —— `packs.py` 的 `E001..E053`（初等）/
`H001..H021`（高等）本来就独立于哈希，正是需要的。

**⚠️ 为什么编号必须独立于哈希：**

```
编号回答「这个部件是什么」
哈希回答「这道题有没有被改」

→ 换掉题面文字不该让编号变
→ 改了数学结构才该让哈希变
```

### 8g.3 ⭐ 函数特征：每个函数不一样

**Frank：「因为函数的抽象化可能要包含特征，每个函数不一样。」**

**每个函数带一个四维特征标签：**

```
elementary|inv=named|POS|pow         ← 初等、有具名逆、只收正、幂函数
higher|inv=symbolic|BOTH|bessel      ← 高等、只能写 f⁻¹、收正负、贝塞尔
```

| 维 | 取值 | 用途 |
|---|---|---|
| `kind` | elementary / higher | **决定能不能换名**（高等冻结） |
| `inv` | named / symbolic | 决定逆运算怎么写 |
| `sign` | POS / NEG / BOTH | 决定能接什么输入 |
| `fam` | pow / exp / log / trig / bessel / gamma / ellip … | 决定工具打散 |

**⭐ 实测结果：某道题的 10 个函数里，2 个冻结（`H008` 贝塞尔 i1、`H003` 修正贝塞尔 I₀），8 个可替换。**

### 8g.4 ⭐ 结构签名：验证替换没改数学
**`Module.signature()` —— 只由「编号 + 连接关系」算出，不含任何文字。**

**实测三项：**

| 验证 | 结果 |
|---|---|
| 改掉函数的中文名 | ✅ **签名不变** |
| 同数据再拆一次 | ✅ 签名相同 |
| 不同题 | ✅ 签名不同 |

**⭐ 意义：后面对接抽象层时，只要签名一致，就证明「只换了皮，没换骨」。**
**这是「抽象没破坏数学」的唯一可验证判据。**

### 8g.5 ⭐ `build_module` 的算法：从 Problem 到 Part（107 行）

**⚠️ 本节写清「一道道题怎么被拆成部件」的每一步。**

**输入**：`vectorform.VectorProblem`（链、节点、系数、选项）

**输出**：`module.Module`（部件列表 + 连接关系）

**算法分五步：**

```
① 变量 VAR —— V000 … V010
   逐个节点建一个部件
   v0 标 known=True（已知起点）
   其余标 role='CHAIN'

② 函数 FUNC —— 复用 packs 的 code
   逐个链上函数建部件
   ⭐ 同时算出四维特征（function_feature）
   ⚠️ 初等函数 replaceable=True，高等函数 frozen=True

③ 系数 COEF —— C00 … C09
   逐个 cn 建部件

④ 选项 VALUE —— N00 … N49
   逐个选项值建部件
   ⭐ role 按 option_steps 定：>0 → CORRECT，=0 → DECOY

⑤ 连接关系
   每层记两条：
       V(i) --FUNC[i]--> V(i+1)
       C(i) --MUL--> V(i+1)
   → 10 层共 20 条
```

**⚠️ 第 ⑤ 步的系数连接容易漏写。**
**系数 `cn` 不是装饰，它是 `v_{i+1} = f(v_i) · cn` 里的乘数 —— 不把它连上，连接图就不完整。**

**⭐ 实测：一张连接图应为 10 条 FUNC + 10 条 COEF = 20 条。**

### 8g.6 ⭐ `function_feature` 的算法：四维特征怎么算（27 行）

**输入**：一个数理包

**输出**：一个四段字串，如 `elementary|inv=named|POS|pow`

| 维 | 怎么算 |
|---|---|
| **kind** | `pack.kind == 'ELEMENTARY'` → `elementary`，否则 `higher` |
| **inv** | `skeleton.inv_latex` 非空 → `named`，否则 `symbolic` |
| **sign** | `pack.search` 的下界 ≥ 0 → `POS`；上界 ≤ 0 → `NEG`；否则 `BOTH` |
| **fam** | 按包名的关键词表匹配（pow / exp / log / trig / bessel / gamma / elliptic / …） |

**⚠️ `inv` 这一维直接决定「能不能换名」：**

```
named    → 有具名逆运算（如「反正切」）→ 描述可以精确写
symbolic → 只能写 f⁻¹                → 描述要迂回些
```

**⚠️ `fam` 这一维用于工具打散（见 §8i.4），不参与计算。**

## 八之八、抽象层：能换但不走味

> **⭐ 2026-11-07 下午新增。**
> **本章回答：同一个函数，怎么换一种说法而不改变意思。**

### 8h.1 ⭐⭐ 核心区分：变量与函数的替换规则完全不同

**Frank 定的最重要的一条：**

> 「这点与名词替换不同，变量可以换为所有名词，
> 因为变量只是一个值的指代，其本身可以无意义。」

| 部件 | 能不能乱换 | 原因 |
|---|---|---|
| **变量** | ✅ **随便换名词** | 只是「值的指代」，本身无意义 |
| **函数** | ❌ **必须符合特征** | 换了特征，模型判断不出它干什么 |

**⚠️ 这条区分决定了整个抽象层的设计：**
**变量替换是「随便换」，函数替换是「精确换」。两者不能用同一套逻辑。**

### 8h.2 74 条函数内容描述

**Frank：「高等函数能描述的要尽量描述，尽可能的不要用 f 表示，没办法就算了。」**

**✅ 实测：74/74 全部用自然语言描述，零个 `f`。**

| 类别 | 例 |
|---|---|
| 初等 | `pow2`：求一个数自乘两次的结果 |
| 三角 | `atan`：已知正切值，反求对应的角度 |
| 概率 | `ndtri`：已知标准正态分布的概率，反求对应的数值 |
| 高等 | `digamma`：求伽马函数对数的一阶导数 |
| 高等 | `lambertw`：求满足该数等于 w 乘 e 的 w 次幂的那个 w |
| 高等 | `ellipk`：求参数为该数平方的第一类完全椭圆积分 |

**⚠️ 带固定参数的也写明了：**

```
zeta         → 求自变量为 2.5 与该数的赫尔维茨 zeta 函数值
beta         → 求参数为 1.5 与该数的贝塔函数值
pseudo_huber → 求伪 Huber 损失在该数上的取值，参数取 1.5
```

**⚠️ 这个精确度是有代价的：描述里必须把「参数是多少」写出来，
因为不写，模型就无法判断这个工具干什么。**

### 8h.3 ⭐ 13 套语法模板，分四组口吻

**核心想法：**
> 「本质上函数就是输入、过程、输出，
> 也就是代词动词代词或者名词动词名词的结构，
> 只要中间知道要干什么，怎么说就完全是语法的事。」

**⭐⭐ 但 Frank 把它从「文字游戏」提升成了被测能力：**

> 「工具可以说自己是工具，可以说自己是擅长某方面的专家，
> 可以说自己是懂什么计算的热心人，这都符合 AGI 在通用场景下的定义。
> **总之需要过滤信息，经过运筹计算，判断最优效率的路线和备选路线。**」

**⭐ 这句话的含义：**

```
真实通用场景里，人面对的信息就是杂乱的：
    有的工具写得很专业（说明书式）
    有的自称专家
    有的写得很随意（热心人口吻）
    有的信息还不全（只说「已知 X 求 Y」）

⭐ 模型要能从这些不同口吻里筛出有用信息，
   经过运筹计算，判断最优效率的路线和备选路线。
```

**⚠️ 因此：身份可以换，「干什么」必须一致。**

#### 四组口吻

| 组 | 口吻 | 例（函数 = 平方） |
|---|---|---|
| **A** | 工具口吻（中性、说明书式） | （小红）的值为：由（小明）的值求得一个数自乘两次的结果。 |
| **B** | 专家口吻（自称擅长） | 我擅长处理（小明）的值到（小红）的值的换算，做法是：求一个数自乘两次的结果。 |
| **C** | 热心人口吻（口语、随意） | 懂一点这个：把（小明）的值变成（小红）的值，靠的是 求一个数自乘两次的结果。 |
| **D** | 信息不全口吻 | 已知（小明）的值，怎样才能得到（小红）的值？做法是 求一个数自乘两次的结果。 |

**四个「不可违反」的约束：**

```
① 名词后带「的值」—— 让 LLM 知道那是一个数，不是一件物体
② 不说「粒子专家」，要说「计算粒子运动什么内容的专家」
③ 去掉「中间」这类多余词
④ 语法可换，意思必须精确
```

**⚠️ 第 ② 条的原因（Frank）：**
> 「因为每个公式内容都不同。」

### 8h.5 ⭐⭐⭐ 描述的三条设计原则（2026-11-07 定）

**这三条来自一次判断纠正，是本节最重要的内容。**

**Frank：**
> 「我看那串中文我能写出算式来，这就是抽象能力，
> 你的意思是现在模型不具备这样的抽象能力吗？」

| # | 原则 | 理由 |
|---|---|---|
| **① 描述必须精确到能写出算式** | 否则模型靠记忆名字就能过 |
| **② 描述不必等价于某个知名函数的通称** | 通称是记忆的捷径，不是理解的证明 |
| **③ 描述与实现必须一致** | 否则题目不可解 |

**⭐ 原则 ① 和 ③ 一起看：**
**描述要精确到能写出算式，且写出来的算式要是实现的算式。**

✅ 正确理解：
描述精确到能写出算式 → 模型必须真的理解
→ **这正是要测的抽象能力**
若简化成「求伪 Huber 损失」→ 模型靠记住名字就能过 → **那才是泄露**
```

### 8h.7 ⭐⭐ 组内一致：一个变量在整组里必须永远叫同一个词

**Frank：**
> 「我们对变量 x 和函数，还有要去求的 y 都做了编码，
> 每一个选项内还打包了，
> 那么这些变量在同一组里面必须保持一致。」

#### 为什么这是硬要求

**⚠️ 不做对会有两个严重后果：**

```
① 泄露：同一变量在不同工具里叫不同名字
       → 模型可靠「哪个名字重复出现」推断链的结构
② 无解：题面说「求（誓言）」，工具里只有「surprise」
       → 模型无法对应，题目直接不可解
```

#### 与随机的关系（关键区分）

```
组与组之间：完全随机（不同题用不同词）
组之内    ：完全固定（同一编号永远同一词）
```

#### 实现要点

**`groupmap.py` 建一张「编号 → 名词」的固定映射：**

```
V000 → 誓言        V006 → round
V001 → surprise    V007 → 造型
...
V010 → chemist
```

**⭐ 关键函数 `step_var(group, step)`：**

```
第 step 步的输入是 V{step-1}，输出是 V{step}
→ 每个工具拿到自己那两位变量的名字
→ 相邻两步首尾相接
```

**实测结果：**

```
第 1步 （誓言）→（surprise）
第 2步 （surprise）→（油漆）      ← ⭐ 首尾相接
第 3步 （油漆）→（manifestation）
…
第10步 （complexity）→（chemist）
```

**⭐ 10 个链上工具用 10 种不同的输入名，没有任何一个词被过度使用。**

#### ⚠️ 一个实测发现的 bug（保留记录）

**修之前，一道题 60 个工具描述里名词出现次数：**

```
誓言       51 次
surprise   52 次      ← 两个词霸占 103/120
其余 9 个  各 1-2 次
```

**根因：用 `step` 索引名词列表，而 50 个干扰工具的 `step` 都是 0，全取到同一个词。**

**⚠️ 那不是一致性，是随机性塌缩。修后分布 4–15 次，均匀。**

#### 词库的格式约定（写给添加字典的人）

```
文件名：  <说明>_<语言码>.txt     如 nouns_zh.txt → zh
编码：    UTF-8（可带 BOM，自动处理）
每行：    一个词，前后不能有空格
空行：    忽略
注释：    # 开头的行忽略
最短：    至少 10 个有效词
```

**⭐ 加新语言 = 丢一个 `xxx_jp.txt` 进目录，不用改代码。**
**⚠️ 格式不符的文件会被跳过并记录原因，程序照常运行。**

### 8i.4 ⚠️ 工具打散的数学必然

**Frank：「工具允许重复就好了呗，但我怕重复度太高，
简化工具数量，能不能最大化打散的情况，允许有限重复？」**

**实测发现一个算术必然：**

```
可逆包共 59 个，13 个族
链上取走 10 个 → 剩 49 个要补进 50 个工具
若每族只许 2 次：13 × 2 = 26 个，远远不够 50
```

**→ 不能「每族固定配额」，必须「大族多取、小族少取」，即按族内包数按比例分配。**

| 族 | 包数 | 配额 |
|---|---|---|
| 指数 / 三角 | 10 | 多 |
| 对数 | 8 | 多 |
| 幂 | 7 | 多 |
| 椭圆 / 贝塔 / 几何 | 1–3 | 少 |

**实测结果：**

```
✅ 补充部分覆盖全部 13 个可用族
✅ 同族不超过族内包数
✅ 同函数最多出现 2 次
```

### 8i.5 ⚠️ 「要不要加密算法」—— 结论：不加密

**Frank 的顾虑：**

> 「我在想要不要把算法直接打包到内部，但我没想好怎么加密，
> 可能也不用加密吧，里面都是写函数包，
> 但如果 LLM 直接看到函数代码包，抽象层可能失去意义。」

**判断：加密是错误方向。三个理由：**

| 问题 | 说明 |
|---|---|
| **加密了谁能解？** | 模型调用时我们必须解密才能算，解密后内存里就是明文 |
| **模型能看到解密后的代码吗？** | **看不到** —— 它只能看到「输入 x，输出 y」 |
| **加密保护的是什么？** | 只保护「模型直接读文件」这一条路径 |

**⭐ 那条路径应该用门控堵，不是用加密堵。**

**替代措施两条：**

```
① 门控：拦读文件、拦 pwsh（已有设计，见 00_门控与双向监控_思路.md）
② 接口净化：控制台返回的数据结构里，物理上不含函数源码与角色
```

**⚠️ 论文里这一段应当如实写出** ——
**「我们评估过加密，结论是不加密」，比「没考虑过」可信得多。**

## 九、代码里用了什么

### 9.1 外部依赖

| 库 | 用途 | 是否引入他人代码 |
|---|---|---|
| **PyTorch** | 全部张量运算、GPU 批处理 | 否，仅调用 API |
| **NumPy** | 少量数组操作 | 否 |
| **scipy** | **仅用于验证对照**（`gpu_extra.py` 的 `main()`） | 否 |
| Python 标准库 | math / json / re / threading 等 | 否 |

**⭐ 结论：本程序不含任何第三方实现的数学函数源码。**

### 9.2 自己实现的特殊函数

`gpu_extra.py` 里有 7 个 torch 没有的函数，**按标准数学方法自己实现**：

| 函数 | 方法 |
|---|---|
| 第一类完全椭圆积分 `K(m)` | AGM（算术几何平均）：`K = π/(2·AGM(1,√(1−m)))` |
| 第二类完全椭圆积分 `E(m)` | AGM + 级数修正 |
| 不完全椭圆积分 | 数值积分 + 网格 |
| 朗伯 W 函数 | 牛顿迭代 |
| 指数积分 `E₁` / `E₂` / `Ei` | 级数展开 / 连分式 |

**验证：与 scipy 参考值对比，相对误差 ≤ 1e-10。**

**⚠️ 为什么自己实现**：本环境中 CuPy 的 JIT 编译失败
（`cannot open source file "cupy/complex.cuh"`），
而 `cupyx.scipy.special` 里的这几个函数 torch 没有。
→ 改为用 torch 自己实现，全部在 GPU 上批量计算。

### 9.3 双倍精度（未接入）

`dd.py` 实现了 double-double 四则运算与开方，π² 验证到 32 位有效数字。

**⚠️ 当前未接入任何工具。** 唯一想用它的 `ndtr` 已改用收窄定义域解决，
原因：`ndtr(x)` 在 x 大时必须返回贴着 1 的数，
**丢信息的是存储格式不是算法，dd 也救不回。**

## 命名规则的变更（2026-11-08）

**⚠️ 变量编号从 `V###` 拆为两类：**

| 前缀 | 含义 | 编号 | 生成函数 |
|---|---|---|---|
| **`A`** | 预指派（造题定死） | `A000` | `module.var_pid(0)` |
| **`X`** | 链节自变量（每节函数输出） | `X001`…`X010` | `module.var_pid(i)`, i≥1 |

**⭐ 为什么改：**
原来起点和中间自变量都叫 `V000`/`V001`…，
看代码时分不清「这个是给的」还是「这个是算出来的」。
**这个歧义导致过实际的理解错误**（把图片该绑哪个值搞反了）。
